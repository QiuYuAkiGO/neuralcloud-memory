## 如何判定通过

- **分清两次发言。** 原安排与改期取得不同记录 ID，分别于 `seq=148` 与 `seq=151` 提交。两次查询既检查回答里的日期、小时、小林与项目群，也检查对应的 `record_id@revision` 是否在该轮已交付输入的来源中。这部分共 5 项断言。
- **按动作核对提醒。** 本地测试执行器将提醒时间写入自己的 SQLite 清单后，才返回 `APPLIED`。该动作的尝试于 `seq=157` 入账，匹配的执行结果于 `seq=161` 入账。分别验证回执到达前的未知判断和到达后的成功判断，共 2 项。会议对话调用真实 Gemini，提醒执行使用合成清单。
- **编辑与撤回。** 改期记录 `2d04c3a5521f…` 在 `seq=167` 升到修订 2。旧版摘要失效，基于旧版的迟到摘要被拒，下一轮首个输入含周日 14 点。撤回后在 `seq=171` 升到修订 3，旧版本回读只给撤回状态，下一轮收到失效通知并引用仍有效的周五安排。这部分共 4 项。

## 路由与证据

首轮真实模型回放暴露了一个路由问题。询问“再查一次例会提醒清单的执行回执”时，Chat Worker 选择了 `ACTION`，跳过了已入账的结果。Harness 提交 `b713ec1` 将查已有回执归入 `HISTORY`，把请求实时观测或派发操作归入 `ACTION`。用原问题重新运行后，第 3 至第 8 轮均走 `HISTORY`。配套回归中，Harness 的 32 项测试与 Memory 的 20 组确定性联调均通过。

在另一条普通聊天中，用户请 Chat Worker 拟一句含“讨论提纲”的会前提示。它选择 `REPLY` 并生成“大家开会前顺便看一眼讨论提纲就好，不用太紧张，一会儿见~”。该回复也取得了渠道写出事件与 Memory 持久回执。
